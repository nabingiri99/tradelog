1. What the Project Is

TradeLog is a trading journal web application. A trader records every trade (entry/exit prices, stop loss, target, pair, session, direction, result, notes, screenshots, psychology) and then reviews statistics and performance through dashboards, analytics, a rules checklist and backtest tools.

The application is a frontend‑backend separated app:

  • Frontend (frontend/) — React single-page application (SPA).
  • Backend (backend/) — REST API built with Express, exposing JWT-authenticated endpoints.
  • Database — MongoDB (Mongoose ODM). Each user’s data is scoped and isolated from every other user.

6. Request Flow — End to End

Every screen request follows the same path:

  1. Browser component calls a hook (useAuth(), useTrades()).
  2. Hook calls the API client frontend/src/lib/api.ts.
  3. api.ts reads the saved JWT and calls fetch("/api/...") with Authorization: Bearer <token>.
  4. Vite dev server proxies /api/* → http://localhost:5000.
  5. Express middleware chain: helmet() → cors() → express.json() → router → route → protect (JWT) → controller → Mongoose → MongoDB.
  6. JSON response returns; on 401 the API client clears the token (auto-logout).
  7. Component updates state; Recharts / tables re-render.
1
Component — e.g. TradeLog calls const { trades, addTrade } = useTrades().
2
Context — TradeProvider runs the optimistic update and calls the client.
3
API client — api.trades.create(trade) → fetch('/api/trades', { method: 'POST', headers: { Authorization: 'Bearer ...' } }).
4
Vite proxy — rewrites the request to http://localhost:5000/api/trades.
5
Backend — tradeRoutes.js → protect verifies JWT and loads req.user → validateTrade checks the payload → tradeController.createTrade.
6
Mongoose — Trade.create({ user: req.user._id, ... }) inserts into MongoDB.
7
Response — 201 { success, message, data: trade } returns; TradeProvider replaces the optimistic record with the server-confirmed one.

7. Authentication Flow

7.1 Registration

1
User fills Login.tsx register form (name, email, password).
2
AuthProvider.register() → api.auth.register() → POST /api/auth/register.
3
Backend validates (email regex, password ≥ 6 chars). Duplicate email → 409.
4
Password hashed with bcrypt.hash(password, 10); only the hash is stored.
5
User saved; a JWT is signed: jwt.sign({ id }, JWT_SECRET, { expiresIn: '7d' }).
6
Response: 201 { success, token, data: user }. Frontend stores the token and sets the session.

7.2 Login & “Remember me”

1
POST /api/auth/login with { email, password }.
2
Backend finds the user by email, compares with bcrypt.compare(). Wrong credentials → 401.
3
Success returns a JWT. Frontend stores it:
  • Remember me = on → localStorage (persists across browser restarts).
  • Remember me = off → sessionStorage (cleared when the tab closes).
4
AuthProvider sets user; protected routes now render.

7.3 Session restore (page refresh)

1
On mount, AuthProvider checks for a stored token (getAuthToken()).
2
If found, it calls GET /api/auth/me (JWT in the header) to fetch the user profile.
3
Valid token → session restored. Invalid/expired → token cleared, user redirected to /login.

7.4 Profile update & password change

  • PUT /api/auth/profile — protected; updates the logged-in user’s name.
  • PUT /api/auth/password — protected; verifies the current password, re-hashes and stores the new one.
Security notes: the toJSON transform on the User model strips passwordHash from every API response; passwords are only ever stored as bcrypt hashes; the backend refuses to start without a JWT_SECRET; helmet sets secure HTTP headers.

8. Trade Management Flow

All trade endpoints are behind protect. Every query filters by user: req.user._id, so each account only ever sees and modifies its own trades (server-side isolation).

8.1 Trade fields (shared schema)

The frontend type frontend/src/types/Trade.ts mirrors the backend models/Trade.js exactly: id, date (YYYY-MM-DD), entryTime, pair, session (London / NewYork / Overlap / Other), direction (Buy / Sell), zoneType (Supply / Demand), entry, stopLoss, target, result (Win / Loss / BreakEven / Open), rr, notes, tags[], mindset { before, after }, emotion, reason, screenshot, isValidRuleTrade.

Trade _ids are client-generated UUIDs stored as strings. This keeps CSV/JSON import/export round-trips stable (an imported trade keeps its original id).

8.2 Creating a trade

1
TradeProvider.addTrade(trade) generates crypto.randomUUID() and applies the change optimistically (instant UI).
2
POST /api/trades → validateTrade → Trade.create({ user: req.user._id, ...trade }).
3
On success the server-confirmed trade replaces the optimistic one. On failure the optimistic trade is rolled back and an error banner shows.

8.3 Updating / deleting

  • PUT /api/trades/:id — optimistic in-place update; reverted if the server rejects it.
  • DELETE /api/trades/:id — optimistic removal; kept for undo, restored if the request fails.
  • DELETE /api/trades — clear all trades for the current user.
  • Undo — deleted trades are remembered in lastDeleted; undoDelete() re-imports them via POST /api/trades/bulk.

8.4 Bulk import (CSV / JSON)

1
User drops a file. csv.ts detects the format:
  • TradeLog export (has id, result, rr columns) → parseCsv.
  • Broker export (date/symbol/entry...) → parseBrokerCsv auto-maps columns and computes rr/result.
  • JSON → array of trades, or { trades: [...] }.
2
Rows are de-duplicated against existing trade ids.
3
POST /api/trades/bulk with { trades: [...] } → Trade.insertMany(docs, { ordered: false }).
4
Fresh trades appear in the list; count returned to the user.

8.5 Listing & filtering

GET /api/trades supports query filters: search (regex on pair), direction, result, startDate/endDate, and whitelisted sort fields (e.g. -createdAt).

15. MongoDB — Local vs Atlas (current status)

Default setup (recommended): the project runs fully on a local MongoDB (mongodb://127.0.0.1:27017/tradelog, MongoDB 8). This sandbox preview runs this way, and the included scripts (scripts/setup-local-db.sh / scripts/setup-local-db.ps1) install and start local MongoDB on any machine. Atlas is optional and just a MONGO_URI switch.

To switch to MongoDB Atlas instead of local:

  1. Set MONGO_URI in backend/.env to your Atlas cluster string.
  2. Whitelist your machine’s public IP under Atlas → Network Access (already done for 27.34.73.7/32).
  3. Restart the backend; new accounts and trades are then stored on Atlas.
Note: data written to the sandbox’s local MongoDB does not automatically move to Atlas. Export your trades (CSV) in the app and re-import them after registering on Atlas, or start fresh. The current backend/.env is gitignored and keeps the sandbox-local URI active.

18. End-to-End Scenario Walkthrough

A complete example: a trader opens the app, signs up, records a trade, reviews analytics, and backs up data.

Scenario A — First run

  1. Open the frontend (Vite dev server, port 5173).
  2. No stored token → AuthProvider.restoring resolves immediately, user = null, ProtectedRoute redirects to /login.
  3. Trader fills the register form. AuthProvider.register() → POST /api/auth/register.
  4. Backend hashes password, creates User, returns 201 + JWT.
  5. Token stored, user set. App re-renders and TradeProvider fetches GET /api/trades (empty list for a new user).
  6. Dashboard renders with zeroed stats.

Scenario B — Log a trade

  1. Trader opens /add, fills the form (pair, direction, entry, stop loss, target, result, notes, tags, psychology).
  2. Submit → TradeProvider.addTrade(): a UUID is generated, the table shows the trade instantly (optimistic).
  3. POST /api/trades persists it under user: req.user._id.
  4. Confirmed record replaces the optimistic row. Stats recompute from trades.

Scenario C — Review performance

  1. Trader opens /analytics.
  2. analytics.ts computes win rate, average RR, profit/loss from the current trades state.
  3. Recharts renders the equity curve and candle chart from the same array.

Scenario D — Backup / migrate

  1. In /log or Profile, the trader exports a CSV (tradesToCsv) containing trade ids.
  2. BackupReminder counts trades logged since the last export and nudges the trader to export.
  3. To migrate to Atlas: register a new account there, then import the CSV → parseCsv → POST /api/trades/bulk → trades restored with their original ids.

19. Security & Reliability Summary

  • AuthN: JWT (HS256, signed with JWT_SECRET), verified on every protected route.
  • AuthZ: all trade queries filter by user; cross-user access returns 404.
  • Passwords: bcrypt hashed, never returned by the API.
  • Headers: helmet; CORS restricted to configured origins.
  • Input: schema enums + positive-number validation at the middleware and Mongoose levels.
  • Resilience: centralized error handler maps Mongoose errors (validation, cast, duplicate key) to clean HTTP responses; async errors are caught by asyncHandler.
  • Frontend: optimistic updates roll back on failure; bulk operations are de-duplicated; 401 auto-clears the session.
